Downloads silently blocked: a rule-priority bug

  • Terraform
  • Zero Trust
  • Audit logs
  • Root-cause analysis
Problem
A group was meant to download files to their laptops. Their rule allowed it, yet downloads were blocked and nothing said why.
Approach
  • Read the audit logs to see which rule the traffic actually matched, instead of guessing from the rule I expected.
  • Found an earlier, broader rule matching first. Rules are evaluated top-down and the first match wins.
  • Moved the specific rule above the broad one in Terraform. No group's permissions changed.
Result
Downloads worked after a small, reviewed change that went to develop first. The same method also caught a wildcard-domain rule that was swallowing traffic meant for newer rules, which I replaced with an explicit subdomain allowlist.

Beyond this one bug, the controls I have shipped as code:

Clipboard DLPRegex detectors limiting copies to 512 and 1,024 characters, applied across 12 access rules. Tested on real ticket text: 409 characters allowed, 543 blocked.
Device postureDisk encryption, EDR and agent checks for Linux, macOS and Windows, rebuilt from manual UI settings into Terraform.
Upload and download profilesRestricted uploads with malware scanning, and a profile that lets files be previewed but not moved elsewhere.
Scoped exceptionsApp-level rules instead of edits to shared profiles, to keep the blast radius small.

Upgrading a Terraform provider across a major version

  • Terraform
  • Change management
  • Provider debugging
Problem
The provider was on 0.42.0 and needed to reach 1.6.0. A jump like that can change how existing resources are planned, and the code manages live security policy.
Approach
  1. Bump the provider and fix the lock-file checksum mismatches.
  2. Run the plan on develop and read every proposed change.
  3. Confirm zero resources would be destroyed.
  4. Promote to production only after review.
Result
The upgrade reached production with a zero-destroy plan. Along the way I fixed an "inconsistent result after apply" error on about 20 resources, and a phantom diff on device posture objects, and documented the trade-off of each workaround for the reviewer.
main.tf (representative)
resource "provider_object" "example" {
  name        = "example"
  description = ""   # set explicitly: null vs "" kept flipping and failed apply

  lifecycle {
    # Provider reports a phantom diff on every plan.
    # Trade-off: real drift on these fields will not show in plan.
    ignore_changes = [ some_field ]
  }
}

Resource and field names are placeholders, not the real schema.

One automation platform, three environments, three trust levels

  • Terraform
  • AWS ECS
  • ALB
  • Route 53
Problem
Access to an external, hosted automation platform had to be reworked when the company moved to a self-hosted one with separate dev, QA and production instances.
Approach
  • Reworked the existing pull request instead of starting a new one, so review history stayed intact.
  • Traced the real domains through a separate infrastructure repository: the ECS module, ALB listener rules, Route 53 records and variable files.
  • Set trust per environment instead of one shared rule.
Result
Each environment gets only the access it needs, and production uploads stay fully blocked until the use case is defined.

A self-healing Python backend on AWS

  • EC2
  • Ubuntu
  • Nginx
  • systemd
  • Let's Encrypt
Problem
A Python backend that parses and validates data needed a production-ready home: reliable, able to recover on its own, and secure.
Approach
  • Set up an Ubuntu EC2 instance and an isolated virtual environment for the app and its dependencies.
  • Ran the app as a systemd service so it starts on boot and restarts after a crash.
  • Put Nginx in front as a reverse proxy to the internal app port.
  • Prepared HTTPS with Certbot and Let's Encrypt.
Result
If the app crashes, systemd brings it back without anyone being paged. HTTPS is the last step: the certificate is issued once DNS propagation finishes.
/etc/systemd/system/app.service (representative)
[Unit]
Description=Python backend service
After=network.target

[Service]
User=ubuntu
WorkingDirectory=/opt/app
ExecStart=/opt/app/venv/bin/python -m app
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
/etc/nginx/sites-available/app (representative)
server {
  listen 80;
  server_name example.com;

  location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;

A failing PR check, and who may approve production

  • GitHub Actions
  • JavaScript
  • Jira REST API
  • Terraform
Problem
A required pull request check kept failing because it only accepted Jira sub-tasks. Separately, production deployment approvers were individual users, which a security review flagged: approvals are OR-based and a person could approve their own change.
Approach
  • Added an opt-in boolean input to the shared composite action. The strict default stays for every other repository, and only one repo opts in.
  • Reworked the logic after senior review so new Jira issue types would not break it.
  • Moved the production approvers into Terraform and switched them from individual users to a team.
  • Sorted out the GitHub token scope and SAML SSO authorization needed to push workflow changes.
Result
The same strict checks everywhere, with one deliberate exception, and central governance of who can approve production.
action.yml (simplified)
name: Check Jira issue
inputs:
  allow-any-issue-type:
    description: Accept any Jira issue type, not only sub-tasks
    required: false
    default: "false"   # strict unless a repo opts in
runs:
  using: composite
  steps:
    - uses: actions/github-script@v7
      with:
        script: |
          const strict = "${{ inputs.allow-any-issue-type }}" !== "true";
          // call the Jira REST API, then validate the issue type
environments.tf (representative)
resource "github_repository_environment" "production" {
  repository  = "example-repo"
  environment = "production"

  reviewers {
    # a team, not individual users
    teams = [github_team.platform_approvers.id]
  }
}

How I work

The habits I bring to a team.

  • Small pull requests. One change, a clear title and a description a reviewer can follow without asking me.
  • Develop first. Nothing reaches production before I have seen the plan and the result on develop.
  • Ask before granting. Which group, which app, what access, for how long. One extra question beats over-broad access.
  • Name the trade-off. Wildcard side effects, shared profiles and wide access get flagged before I implement, not after.
  • Root cause over patch. Read the logs, find the rule that actually fired, and fix that.
